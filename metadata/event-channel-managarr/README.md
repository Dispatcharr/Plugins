**Version:** `1.26.3321948` | **Author:** PiratesIRC | **Last Updated:** Nov 28 2026, 20:18 UTC

## Plugin README

A Dispatcharr plugin that automatically manages channel visibility based on EPG data and channel names. It hides channels that currently have no event information and shows channels that do. An optional managed dummy EPG so the guide still shows something useful (event title during the window; "Upcoming at <time>: <title>" before; "Ended at <time>: <title>" after) for channels that never have real EPG assigned.

> [!TIP]
> **New to Dispatcharr plugins?** Start with the **[Dispatcharr Plugin Workflow guide](https://piratesirc.github.io/Dispatcharr-Plugin-Workflow/)**.
> It explains what each plugin and tool does, where they overlap, and what order to use them in.

<sub>The badges count installations that send anonymous usage counts. See <a href="#anonymous-usage-counts">Anonymous usage counts</a>.</sub>

## Features

**Decides visibility from the channel name.** A fully customisable rule list
decides what to hide: a channel that matches any rule in it is hidden, and the
first rule that matches is named as the reason. Rules cover a past date, a date
too far ahead, a name that never carries a date at all, a name too short to describe an event, the wrong day of the week, a
blank or placeholder name, and a pattern you supply yourself. A name carrying a
clock time but no date is hidden once that event's inferred end, plus a grace
period you set, has passed.

**Reads either the channel name or the stream name.** Providers that leave the
channel name fixed and put the game in the stream name are handled by switching one
setting, or by listing just those channel groups in **Stream Name Groups** so other
groups keep reading channel names. On Dispatcharr 0.32.0 or later such a group can
also get its own guide source that reads the stream name.

**Fills the guide for channels that have no EPG.** An optional plugin-managed dummy
EPG source renders the event title during its window, `Upcoming at <time>: <title>`
before it and `Ended at <time>: <title>` after, in the viewer's local time. Channels
whose names claim a different timezone get their own source rather than being pulled
back and forth. Three channel-name layouts are understood: the US form
(`PPV EVENT 12: Title (MM.DD HH:MM AM/PM TZ)`, and bare numbered slots such as
`07 - 8/14 7pm Broncos at Falcons`), the Swedish pipe-delimited form, and the `AT`
form with the date after an `@` (`NHL 01: Kraken @ Red Wings @ 9 Oct 07:00 PM ET`).

**Gives a channel group its own guide source.** Groups whose events are labelled in
different timezones, or that need different durations or title patterns, can each be
mapped to their own dummy EPG source. The plugin creates the source and seeds it from
your settings, then leaves it alone so you can edit it in Dispatcharr. A group you do
not map keeps the shared source.

**Hides duplicates of the same event**, keeping the lowest number, the highest
number or the longest name, whichever you choose.

**Scopes precisely.** Monitor several channel profiles at once, narrow to named
channel groups, skip channels by regular expression, and force chosen channels to
stay visible whatever the rules say.

**Runs on a schedule**, at times you set in Dispatcharr's own timezone, and
optionally straight after each M3U refresh. A cross-process lock means at most one
scan runs at a time across every worker, and a lock left behind by a dead process is
broken automatically after fifteen minutes.

**Reports what it did, and what it ignored.** Every run writes a CSV giving the
action, the reason and the rule for each channel. Channel groups that matched
nothing, and regular expressions that matched nothing, are named in the result and
in the CSV header, so a setting that is quietly doing nothing is visible rather than
silent.

**Previews safely.** Dry Run reports what would change and writes the CSV without
touching a single channel or creating any EPG binding.

**Makes one outbound request, an anonymous usage count.** The plugin talks to Dispatcharr's database
and to one HTTPS endpoint, plugin-stats.dpas.workers.dev, which receives the anonymous usage
count. You can switch that off in settings. See [Anonymous usage counts](#anonymous-usage-counts).

## Anonymous usage counts

The Visibility Changes and Active Installs badges count every install that leaves
the "Share anonymous usage counts" setting (on by default) ticked and runs at
least one action or scheduled scan. Visibility Changes counts the channels this
plugin switched on or off in applied runs, the same transition count the run
ledger records (see the user guide's Run Ledger section). Dry runs and runs that
change no channel are not counted. An M3U refresh sends nothing unless Auto-rescan after M3U refresh is on.

When an action or a scheduled scan finishes, the plugin sends this plugin's
Visibility Changes total and a random id for this plugin on this install to the
plugin author's counter at plugin-stats.dpas.workers.dev. It sends at most once an hour, or ten minutes after the last successful send when a run has just changed channel visibility. A run that finishes inside that gap is not sent later: the total goes out with the first later action or scheduled scan that is an hour past the last successful send, or with a later run that changes visibility once ten minutes have passed.

The server stores that id with the total and the date of the last report, and
keeps them until this install unticks the setting and the delete succeeds, or
until the plugin author removes them by hand. An install that stops reporting
still counts toward Visibility Changes. The connection shows the server your
public IP address; the server uses it only to limit abuse and does not store it
in its database, though when an install first registers it keeps a salted
one-way hash of it (of its /64 block for IPv6) for up to three days. Cloudflare,
which hosts the server, keeps its own request logs. No names, channels, streams,
URLs, providers or settings are sent. The figures are self-reported by installs
and capped by the server, not verified.

What counts as an active install: an install that sent at least one report in
the last 30 UTC days. A badge changes after the server's hourly recount, which
runs at the start of each UTC hour, and Shields may cache the badge for up to an
hour more, so a new report can take up to about two hours to show.

The setting is the last one in the settings form, in its own section. Unticking
it takes effect when the next action or scheduled scan finishes; the plugin then
asks the server to delete this install's figures. Once the server confirms the
delete, the plugin forgets its id, and ticking the setting again later starts a
new one; if the delete could not reach the server, the plugin keeps the id and
retries. The plugin keeps that id and the timing of its reports in the folder
usage/event-channel-managarr/ of its data folder (install_id, sent, backoff, disabled,
delete_backoff, lock); see [Where Event Channel Managarr keeps its files](#where-event-channel-managarr-keeps-its-files). To start a new id, untick the setting and let an action run so the server deletes this install's figures; deleting that folder while the setting is ticked leaves the old figures on the server, and the new id then sends the full total again, so the badge counts it twice.

## Where Event Channel Managarr keeps its files

The plugin keeps its private files in its data folder, `/data/plugins/_data/event-channel-managarr/`. Dispatcharr creates that folder and names it for the plugin's key, `event-channel-managarr`. On the first start after an upgrade the plugin copies the files it used to keep under `/data` into that folder. The copy never deletes, renames or edits an old file, and a file already in the data folder is left as it is. The copy is recorded in `migrated.json` in the data folder.

Inside the data folder:

- `settings.json`: a copy of the saved settings. Dispatcharr's database row is the source of truth; this file is a cache of it.
- `results.json`: the output of the last scan.
- `undated_first_seen.json`: the first-seen record that `[UndatedAge:N]` and `[UndatedEnded]` read.
- `group_sources.json`: the record of the dummy EPG sources the plugin created for each group mapping. The plugin uses it to move a channel back off a source later. Keep it: if it is lost, channels stay where they are and nothing is moved back.
- `ledger.jsonl`: the run ledger, one line per applied run that changed a channel. It is append only and rotates once to `ledger.jsonl.1` at 5 MB. `ledger.offsets.json` and `ledger.lock` are bookkeeping for the copy of the ledger.
- `usage/event-channel-managarr/`: the anonymous usage counter's install id and send record.
- `migrated.json`: when the copy ran, which files it copied and which it could not.

Beside the data folder, in `/data/plugins/_data/`:

- `event-channel-managarr.last_run.json`: the last run of each scheduled time. Every worker reads it, so it sits beside the folder rather than inside it.
- `event-channel-managarr.scan.lock`: the lock that keeps two scans from running at once.

Outside both:

- `/data/exports/`: the CSV exports. Seven plugins share this folder, and the plugin deletes only its own exports from it.

Dispatcharr's **Delete data** option on uninstall removes the data folder. It does not remove the two files beside it.

During the release that moves the files, a worker still running the previous release keeps writing the old files under `/data`. The new release reads both copies of the last-run record and takes both locks, so a scheduled run or a scan that the old worker has started or claimed is not repeated. The old files are safe to delete only when `migrated.json` has an empty `failed` list and none of the old files has changed since the time recorded in it. An old file that still changes means a worker on the previous release is still running.

The old `/data` files were `event_channel_managarr_settings.json`, `event_channel_managarr_results.json`, `event_channel_managarr_undated_first_seen.json`, `event_channel_managarr_group_sources.json`, `event_channel_managarr_ledger.jsonl` (and `.1`), `event_channel_managarr_last_run.json`, `event_channel_managarr_scan.lock` and the folder `/data/plugin_stats/event-channel-managarr/`. Nothing reads `event_channel_managarr_version_check.json` any more, since the update check was removed, so it is not moved.

## Disclaimer

**Event Channel Managarr provides no television content of any kind.** It supplies no channels, no
playlists, no streams, no electronic programme guide data and no provider accounts, and it contains
no list of where to obtain any of those. It bundles no reference data at all: everything it works on
already exists in **your** Dispatcharr installation.

What it reads is channel *names* and the programme data already stored against your channels. It
parses event titles, dates and times out of those names to decide which channels currently
have an event. **It never opens, reads, decodes, records, restreams or redistributes a stream**, and
it never reads a stream URL. **Its only outbound network request is the anonymous usage count** to plugin-stats.dpas.workers.dev, which you can switch off in settings (see [Anonymous usage counts](#anonymous-usage-counts)). The update checker that
once called the GitHub releases API was removed in `1.26.2251616`, along with the code behind it.

What it writes is confined to your own Dispatcharr database and its data directory: channel
visibility in the profiles you select, bindings to a dummy EPG source it manages, and CSV exports, plus one small folder for the anonymous usage count (see [Anonymous usage counts](#anonymous-usage-counts) and [Where Event Channel Managarr keeps its files](#where-event-channel-managarr-keeps-its-files)).
The main scan has a **Dry Run** that writes nothing and exports what it *would* do to CSV. Run that
first. The other actions that change data (**Run Now**, **Remove EPG from Hidden Channels**, **Clear
CSV Exports**, **Cleanup Orphaned Tasks**) each ask for confirmation before they act.
